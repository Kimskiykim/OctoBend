# AI-кодинг: карта сущностей и этапов

---

## 1. Без карты это превращается в кучу

В AI PDLC уже много фреймворков, агентов и локальных практик:

- OpenSpec / Spec Kit / Kiro Specs;
- GigaCode / Codex / Claude Code / Cursor / Cline / Roo;
- Superpowers / GSD / gstack;
- MCP, RAG, CodeIndexer, DeepWiki, RepoPrompt, Repomix;
- CI, проверки контрактов, оценки, ретроспективы, GigaCode /insights, VS Code extension AI Engineer Coach.

Каждый инструмент что-то улучшает, но без общей карты трудно понять:

- какую часть процесса он закрывает;
- какую проблему он решает;
- что остаётся незакрытым;
- как состыковать разные подходы между командами.

Главная мысль:

```text
Сначала концептуальная карта.
Потом инструменты.
```

Без концептов всё выглядит как набор несвязанных практик. С концептами видно, где именно можно улучшать процесс.

Идеальное состояние: агент понимает не только правила конкретного фреймворка, а общую карту работы. Тогда один инструмент можно заменить другим без пересборки всего процесса.

---

## 2. Карта сущностей и этапов AI-кодинга

В любом фреймворке кодинговый агент сталкивается с одними и теми же сущностями и этапами.

| Сущность / этап | Главный вопрос |
|---|---|
| Контекст | Что агент должен знать прямо сейчас, и не перегружено ли окно? |
| Память проекта | Какие знания устойчивые, актуальные и авторитетные? |
| Намерение | Что пользователь реально хочет изменить? |
| Спецификация | Как явно описано новое ожидаемое поведение? |
| Критерии приёмки | По каким критериям поймём, что задача выполнена? |
| Влияние и риск | Что затронет изменение: API, данные, безопасность, другие команды? |
| Исполнение и оркестрация | Как агент выполняет работу: фазы, роли, границы, передача контекста? |
| Проверка и доказательства | Чем доказать, что результат корректен? |
| Актуальность и согласование | Что стало неактуальным после изменения? |
| Обучение и улучшение | Как повторяющиеся ошибки улучшают процесс? |

Эта карта важнее названий фреймворков.

```text
Фреймворки меняются.
Фундаментальные сущности и этапы остаются.
```

Если агент знает эти сущности, он может работать поверх разных реализаций: сегодня OpenSpec, завтра другой подход к спецификациям; сегодня один способ оркестрации, завтра другой.

## 3. Где именно можно улучшать процесс

По каждому этапу можно отдельно искать проблемы, артефакты и инструменты улучшения.

| Этап | Что ломается | Что улучшать | Чем можно помочь |
|---|---|---|---|
| Контекст | агент загрузил не то; контекст протух; окно перегружено шумом | отбор источников, слои контекста, проверка актуальности | MCP, RAG, CodeIndexer, DeepWiki, RepoPrompt, Repomix, пакеты контекста |
| Память проекта | документы, спецификации, ADR и факты расходятся с кодом | авторитетность, владелец, триггеры актуальности, продвижение в память | ревью документов, проверки актуальности, реестр знаний |
| Намерение / спецификация | цель живёт в чате; границы размыты | спецификация изменения, исключения, явное ожидаемое поведение | OpenSpec, Kiro Specs, GitHub Spec Kit |
| Критерии приёмки | критерии непроверяемые или отсутствуют | проверяемые критерии, примеры, крайние случаи | OpenSpec, тестовые сценарии |
| Влияние и риск | агент не видит радиус последствий | затронутые области, владельцы, уровень риска, влияние на контракт | CODEOWNERS, карты зависимостей, CI-проверки, ревью агентом |
| Исполнение и оркестрация | агент сразу пишет код; нет фаз и следа работы | режимы, фазы, границы записи, логи запуска, передача контекста | Superpowers, GSD, gstack, GigaCode, Codex, Claude Code |
| Проверка и доказательства | “тесты прошли” считается готовностью | доказательства, связанные с критериями приёмки, вывод CI, сравнение контракта | CI, GitHub Actions, проверки контрактов, заметки ревью |
| Актуальность и согласование | после слияния протухают документы, спецификации и контракты | обнаружение рассинхрона, обновление, исключение, ревью | чеклист актуальности, проверки документов, ревью OpenSpec |
| Обучение и улучшение | ошибки повторяются | ретро, предложение правила, проверки, оценки или инструмента | GigaCode /insights, VS Code extension AI Engineer Coach, ретро Superpowers, Promptfoo, Langfuse, внутренние оценки |

Так фреймворки перестают конкурировать “в целом” и начинают закрывать конкретные части карты.

Задача не в том, чтобы выбрать один “правильный” фреймворк навсегда. Задача в том, чтобы агент понимал этапы и мог подключать подходящие инструменты как заменяемые модули.

## 4. Пример: изменение API / авторизации

Пусть агенту нужно поменять API авторизации: обновление токена, статусы 401/403 или обязательность заголовка.

Без карты процесс выглядит просто:

```text
запрос -> агент изменил код -> тесты зелёные -> задача закрыта
```

Но по карте видно, что задача шире:

| Этап | Что проверить |
|---|---|
| Контекст | загружены ли код авторизации, тесты, бизнес-требования, архитектура, ADR, OpenAPI, логи, прошлые решения? |
| Намерение / спецификация | описано ли новое поведение и что не входит в задачу? |
| Критерии приёмки | есть ли проверяемые критерии для входа, обновления сессии, выхода и ошибок? |
| Влияние и риск | затронуты ли SDK, потребители, безопасность, модель данных, документы? |
| Исполнение | агент работает по фазам или сразу меняет всё подряд? |
| Проверка | есть ли модульные тесты, интеграционные тесты, сравнение контракта, доказательства ревью? |
| Актуальность | обновлены ли спецификации, контракты, документы или оформлено исключение / ревью? |
| Обучение | если агент забыл обновить контракт, появилась ли новая проверка или правило? |

С картой фраза “тесты зелёные” больше не равна “готово”.

## 5. OpenSpec как часть карты, а не вся карта

OpenSpec важен, потому что хорошо усиливает область:

```text
намерение -> спецификация -> критерии приёмки
```

Но он не обязан закрывать весь AI PDLC.

| Этап | Роль OpenSpec | Что нужно рядом |
|---|---|---|
| Контекст | может ссылаться на спецификации и документы | отбор актуального рабочего контекста |
| Намерение / спецификация | сильная фиксация изменения и ожидаемого поведения | связь с исполнением и доказательствами |
| Критерии приёмки | помогает задать критерии готовности | проверки, тесты, доказательства ревью |
| Влияние и риск | частично виден через изменение и спецификацию | владельцы, карты зависимостей, проверки безопасности и API |
| Исполнение и оркестрация | не основной фокус | процессы на базе Superpowers, GSD, gstack, GigaCode / Codex / Claude Code |
| Проверка и доказательства | может задать ожидаемые проверки | CI, сравнение контракта, отчёты тестов |
| Актуальность и согласование | помогает обновлять спецификации | проверки рассинхрона документов, контрактов и фактов |
| Обучение и улучшение | не основной фокус | GigaCode /insights, VS Code extension AI Engineer Coach, ретро, оценки, изменения процесса |

Вывод:

```text
OpenSpec закрывает важную часть карты,
но процесс AI-кодинга требует связки нескольких способностей процесса.
```

## 6. Как использовать карту

Карта нужна, чтобы улучшать процесс не хаотично, а по конкретным зонам.

Практический способ:

1. Выбрать этап карты.
2. Назвать фундаментальную проблему.
3. Понять, какой артефакт или проверка нужны.
4. Выбрать инструмент, который закрывает именно эту проблему.
5. Проверить, что осталось незакрытым.

Пример:

| Хотим улучшить | Сначала формулируем проблему | Потом выбираем инструмент |
|---|---|---|
| Спецификации | намерение теряется в чате | OpenSpec / Kiro Specs / Spec Kit |
| Контекст | агент тащит шум или устаревшие данные | MCP / RAG / CodeIndexer / DeepWiki / RepoPrompt / Repomix |
| Исполнение | агент сразу пишет код без фаз и передачи контекста | Superpowers / GSD / gstack |
| Проверка | “тесты прошли” без связи с критериями приёмки | CI / проверки контрактов / доказательства ревью |
| Актуальность | спецификации, документы и контракты протухают после слияния | чеклист актуальности / проверки документов |
| Обучение | ошибки повторяются | GigaCode /insights / VS Code extension AI Engineer Coach / ретро / Promptfoo / Langfuse / оценки |

Финальная формула:

```text
Мы улучшаем не “агента вообще”.
Мы улучшаем конкретные этапы AI PDLC.

Фреймворки — это способы усилить отдельные этапы,
а общая карта помогает связать их в один процесс.

Идеальный агент знает карту концепций,
а фреймворки использует как заменяемые адаптеры.
```
