# Компонентная модель AI-кодинга

> Рабочий текст для детальной презентации на базе 4-го слайда. Цель: описать не инструменты, а управляемые области процесса, через которые проходит любое AI-изменение в коде.

---

## 1. Что такое компонент

Компонент — это управляемая область AI-кодинга, у которой есть:

- назначение;
- входы;
- внутренний состав;
- артефакты;
- типовые сбои;
- контрольные вопросы;
- практики улучшения;
- инструменты-адаптеры.

Главная мысль:

```text
Мы описываем не инструменты.
Мы описываем управляемые области процесса,
через которые проходит любое AI-изменение в коде.
```

---

## 2. Сквозной слой управления

Сквозной слой управления — это правила, которые действуют поверх всех компонентов.

Он не является отдельным этапом. Он определяет, кто владеет артефактами, какие действия разрешены, где нужны согласования и какие доказательства обязательны.

Что включает:

- владельцы артефактов;
- права агента;
- согласования;
- риск-ориентированный объём контроля;
- прослеживаемость от запроса до проверки;
- правила работы с памятью;
- утверждённые рецепты работы;
- требования к доказательствам.

Что мы делаем:

- задаём, когда агент может сразу писать код, а когда обязан сначала уточнить задачу;
- определяем, какие задачи требуют спецификации, анализа влияния, проверки безопасности, проверки контрактов;
- фиксируем, какие навыки и рабочие сценарии являются стандартом команды;
- не даём агенту скрыто менять знания проекта или правила процесса.

Ключевой вопрос:

```text
Кто владеет решением, правилом, артефактом и доказательством?
```

## 3. Рабочий контекст

Рабочий контекст — это рабочая проекция задачи: выбранные данные, решения текущей сессии и след уже выполненных действий, которые агент использует, чтобы понять ситуацию, принять решение и выполнить работу.

У контекста есть два смысла:

- контекст в широком смысле — вся информационная среда, из которой агент может брать извлекать знания;
- контекст в узком смысле — то, что агент реально использует сейчас: данные в контекстном окне, context pack, решения сессии и след действий.

Важно:

```text
Контекст не равен истине.

Контекст = выбранные данные + решения сессии + след действий.

Контекст =
выбранные данные
+ решения сессии
+ след действий.

Истина =
авторитетный источник
+ актуальность
+ доказательства.
```

Что попадает в контекстное окно:

- запрос пользователя;
- уточнения;
- правила репозитория;
- системные инструкции;
- инструкции разработчика;
- правила из `AGENTS.md` (GIGACODE.md, CLAUDE.md);
- релевантные фрагменты кода;
- тесты;
- конфиги;
- спецификации;
- архитектурные решения;
- бизнес-требования;
- данные через `MCP`: Confluence, Jira, логи, тестовые системы;
- выводы предыдущих команд;
- изменения в файлах;
- принятые решения в текущей сессии;
- зафиксированные допущения;
- выбранный план;
- отклонённые варианты;
- прошлые действия агента;
- навыки и память агента;
- временные markdown-артефакты агента.

Что не должно попадать бездумно:

- весь репозиторий;
- длинные документы целиком;
- старые summaries агента без доказательств;
- нерелевантные логи;
- сгенерированные summaries без ссылки на источник;
- устаревшие страницы Confluence;
- большие context packs без отбора.

Что мы делаем:

- разделяем контекст по слоям;
- выбираем минимальный релевантный набор;
- отдельно управляем извлечением и навигацией: сначала карта, затем релевантные источники, затем точечные фрагменты;
- отдельно фиксируем решения сессии и не смешиваем их с истиной проекта;
- сохраняем след действий: команды, изменённые файлы, выводы проверок, отклонения;
- сжимаем большие источники в структурированные выжимки;
- оставляем ссылки на источники истины;
- не смешиваем результат поиска и авторитетное знание;
- проверяем актуальность;
- оптимизируем токены.

Как оптимизировать токены:

- сначала загружать карту: файлы, владельцы, релевантные модули;
- затем точечно читать нужные фрагменты;
- большие документы сжимать до фактов, решений и открытых вопросов;
- хранить context pack как артефакт, а в окно класть только нужный фрагмент;
- удалять повторяющиеся summaries;
- держать активное состояние задачи коротким;
- держать решения сессии в компактном списке: принято, почему, чем подтверждено;
- не тащить весь журнал действий в окно, а оставлять короткий trace с ссылкой на подробный лог;
- отделять “что известно” от “что нужно проверить”.

## 4. Память и знания проекта

Память проекта — это долговременное авторитетное знание, из которого агент может собирать рабочий контекст.

В модели есть три разных вида памяти:

- память агента — что агент умеет и помнит о стиле работы;
- память проекта — что проект устойчиво знает и обещает;
- сессионная память — что было решено и сделано в текущей сессии.

Что включает:

- код как источник фактической реализации;
- стабильные спецификации;
- API-контракты;
- схемы данных;
- архитектурные решения;
- архитектурные документы;
- бизнес-требования;
- инструкции эксплуатации;
- карты владения кодом;
- правила процесса;
- проверенные факты;
- карты кода.

Отличие от контекста:

```text
Память проекта долговечна.
Контекст зависит от конкретной задачи.
```

Что мы делаем:

- определяем уровни авторитетности;
- назначаем владельцев;
- добавляем доказательства;
- фиксируем триггеры устаревания;
- не позволяем агенту превращать временную заметку в истину проекта без ревью;
- продвигаем полезные выводы из задач в память только после проверки.

Типовые сбои:

- документация расходится с кодом;
- архитектурное решение описывает старое состояние;
- сгенерированный markdown воспринимается как истина;
- нет владельца знания;
- нет даты актуальности;
- нет связи с доказательствами.

Контрольные вопросы:

- Это источник истины или подсказка?
- Кто владелец?
- Когда обновлялось?
- Чем подтверждено?
- Что делать при конфликте с кодом?

## 5. Намерение, спецификация и критерии готовности

Это слой, который превращает запрос пользователя в проверяемое изменение.

Короткие определения:

- намерение — зачем пользователь хочет изменение и какую проблему он решает;
- спецификация — что именно должно измениться в поведении системы;
- критерии готовности — как проверим, что изменение выполнено.

Что включает:

- цель изменения;
- границы задачи;
- что не входит в задачу;
- новое ожидаемое поведение;
- исключения;
- граничные случаи;
- критерии готовности;
- примеры сценариев;
- предположения;
- открытые вопросы.

Что мы делаем:

- не даём задаче остаться только в чате;
- фиксируем ожидаемое поведение;
- явно пишем границы;
- переводим требования в проверяемые критерии;
- связываем критерии готовности с будущей проверкой.

Пример:

```text
Плохо:
“поправь авторизацию”

Лучше:
“refresh token должен обновлять session без повторного login;
401 возвращается при истекшем access token;
403 возвращается при недостаточных правах;
logout инвалидирует refresh token;
не меняем модель ролей.”
```

Типовые сбои:

- агент сразу пишет код;
- цель понята приблизительно;
- критерии готовности отсутствуют;
- критерии нельзя проверить;
- границы задачи расползаются.

Инструменты-адаптеры:

- OpenSpec;
- Kiro Specs;
- GitHub Spec Kit;
- шаблоны описания изменения;
- тестовые сценарии.

## 6. Влияние, риск и владельцы

Это оценка радиуса последствий изменения.

Что включает:

- затронутые модули;
- API;
- контракты;
- схемы данных;
- миграции;
- безопасность;
- права доступа;
- владельцы кода;
- потребители;
- команды;
- обратная совместимость;
- обязательные проверки;
- уровень согласования.

Что мы делаем:

- строим карту влияния до изменения;
- определяем уровень риска;
- выбираем объём контроля;
- подключаем владельцев;
- задаём обязательные проверки;
- решаем, нужен ли дизайн-ревью, security review или contract review.

Пример риск-ориентированного контроля:

```text
Низкий риск:
короткая заметка + локальные тесты.

Средний риск:
спецификация изменения + критерии готовности + анализ влияния + проверка.

Высокий риск:
дизайн + согласование владельцев + проверки безопасности/контрактов + контроль актуальности.
```

Типовые сбои:

- агент меняет локальный файл и не видит внешний контракт;
- ломается интеграция другой команды;
- не обновляется OpenAPI;
- отсутствует согласование;
- проверки не соответствуют риску.

## 7. Исполнение и оркестрация

Исполнение — это не “агент пишет код”. Это управляемый запуск работы.

Что включает:

- фазы работы;
- роли и режимы агента;
- границы среды выполнения;
- права;
- согласования;
- команды;
- журнал решений;
- журнал отклонений;
- передача состояния;
- границы записи;
- использование инструментов.

Фазы могут быть такими:

```text
уточнить → собрать контекст → оценить влияние → спланировать → реализовать → проверить → согласовать знания → передать состояние
```

Что мы делаем:

- параметризируем поведение агента;
- решаем, когда он может писать код;
- ограничиваем область изменений;
- фиксируем команды и решения;
- требуем передачу состояния при смене исполнителя;
- используем навыки как режимы исполнения.

Где лежат навыки:

- как способность агента — в рабочем контексте;
- как применяемый сценарий работы — в исполнении;
- как утверждённый стандарт команды — в сквозном слое управления.

Типовые сбои:

- агент сразу пишет код;
- нет фаз;
- нет следа работы;
- невозможно понять, почему принято решение;
- агент меняет лишние файлы;
- следующий агент не понимает состояние задачи.

Инструменты-адаптеры:

- GigaCode;
- Codex;
- Claude Code;
- Superpowers;
- GSD;
- gstack.

## 8. Проверка и доказательства

Проверка — это действия. Доказательства — это артефакты, которые можно посмотреть и проверить.

Что включает:

- модульные тесты;
- интеграционные тесты;
- проверки контрактов;
- проверку типов;
- линтер;
- проверки безопасности;
- ручную проверку;
- вывод CI;
- скриншоты;
- логи;
- заметки ревью;
- отчёт о проверке.

Что мы делаем:

- связываем проверки с критериями готовности;
- сохраняем доказательства;
- явно пишем, что не проверено;
- не считаем “тесты зелёные” полным доказательством;
- проверяем именно риск изменения.

Формула:

```text
Готово =
критерии готовности закрыты
+ доказательства приложены
+ известные пробелы названы.
```

Типовые сбои:

- тесты прошли, но критерии готовности не проверены;
- проверка не покрывает изменённый контракт;
- доказательства потеряны в чате;
- агент утверждает “проверено”, но нет вывода команд;
- CI зелёный, но документы или спецификации протухли.

## 9. Объяснение и взаимодействие с человеком

Объяснение — это не декоративный текст в конце работы агента. Это часть управляемого цикла, через который человек понимает, что агент понял, что делает, где есть риск и чем подтверждён результат.

Взаимодействие с человеком — это двусторонний control loop между человеком и агентом.

Что включает:

- уточнение намерения;
- объяснение найденного контекста;
- объяснение плана;
- промежуточные статусы;
- вопросы и эскалации;
- запрос согласований;
- объяснение решений и trade-offs;
- объяснение отклонений от плана;
- объяснение diff;
- итоговое summary;
- handoff следующему человеку или агенту.

Что мы делаем:

- не скрываем ход рассуждений и принятые решения внутри агента;
- показываем, какой контекст был использован;
- явно называем допущения;
- связываем результат с критериями готовности;
- прикладываем доказательства;
- отделяем “я сделал” от “это проверено”;
- даём человеку возможность вовремя остановить scope drift;
- передаём состояние так, чтобы работу можно было продолжить.

Формула:

```text
Агент выполняет изменение
+ объясняет, что понял
+ показывает, что собирается делать
+ фиксирует решения
+ объясняет отклонения
+ предъявляет доказательства
+ передаёт итог в понятном виде.
```

Типовые сбои:

- агент молча пишет код;
- человек не понимает, почему изменены конкретные файлы;
- нет промежуточных статусов;
- риск обнаруживается только в конце;
- итоговое сообщение не связано с критериями готовности;
- handoff не позволяет продолжить работу.

Инструменты-адаптеры:

- GigaCode;
- Codex;
- Claude Code;
- Cursor;
- IDE chat;
- pull request summaries;
- handoff templates;
- review assistants.

## 10. Контроль рассинхрона знаний

Это слой после изменения: что стало неактуальным?

Что включает:

- спецификации;
- документы;
- контракты;
- архитектурные решения;
- факты;
- карты кода;
- инструкции эксплуатации;
- OpenAPI;
- сгенерированные context packs;
- исключения.

Что мы делаем:

- ищем рассинхрон между кодом и знаниями;
- обновляем документы и контракты;
- оформляем исключение, если не обновляем;
- продвигаем полезные выводы в память проекта;
- архивируем временные артефакты изменения.

Примеры рассинхрона:

```text
код изменился, спецификация старая;
OpenAPI не соответствует реализации;
Confluence говорит старое поведение;
summary агента не подтверждается diff;
архитектурное решение больше не описывает актуальное состояние.
```

Типовые сбои:

- задача закрыта после кода;
- документы забыты;
- контракт не обновлён;
- старые сгенерированные summaries остаются в контексте будущих задач;
- память проекта деградирует.

## 11. Обучение процесса

Обучение процесса — это не скрытая самомодификация агента. Это управляемый контур улучшения.

Что включает:

- повторяющиеся ошибки;
- ретроспективы;
- insights;
- оценки;
- рекомендации coach-инструментов;
- предложения по изменению процесса;
- новые проверки;
- новые шаблоны;
- новые рецепты;
- предложения по инструментам.

Что мы делаем:

- собираем повторяющиеся сбои;
- формулируем улучшение процесса;
- отправляем его на ревью;
- внедряем как правило, рецепт или проверку;
- измеряем эффект.

Примеры:

- агент часто забывает обновлять OpenAPI → добавить проверку актуальности;
- агент не видит владельцев затронутого кода → усилить шаблон анализа влияния;
- агент перегружает контекстное окно → ввести бюджет контекста и формат context pack;
- агент пишет код до спецификации → ввести правило: задачи с высоким риском требуют спецификацию изменения.

Инструменты-адаптеры:

- GigaCode /insights;
- VS Code extension AI Engineer Coach;
- Promptfoo;
- Langfuse;
- ретро Superpowers;
- внутренние оценки.

## 12. Эффективность агента и человека с агентом

Эффективность нужно измерять на трёх уровнях:

- эффективность агента;
- эффективность человека с агентом;
- эффективность всей системы человек-агент.

Эффективность агента — это насколько хорошо агент превращает намерение в корректное, проверенное и объяснимое изменение при разумной цене контроля.

Что измеряем:

- точность понимания намерения;
- качество собранного контекста;
- компактность контекстного окна;
- количество лишних действий;
- first-pass correctness;
- количество переделок;
- качество проверки;
- полноту доказательств;
- качество объяснений;
- стоимость в токенах, времени и командах.

Эффективность человека с агентом — это насколько человек быстрее, точнее и спокойнее доводит engineering-задачу до результата, используя агента как инструмент анализа, исполнения, проверки и объяснения.

Что измеряем:

- скорость перехода от идеи к проверенному изменению;
- снижение ручной рутины;
- качество постановки задачи;
- качество контроля scope;
- время на объяснение задачи агенту;
- время на review результата;
- количество переделок;
- понятность результата;
- обоснованное доверие к результату;
- снижение когнитивной нагрузки;
- помощь в принятии инженерных решений.

Эффективность системы человек-агент — это насколько вся связка даёт качественный, проверяемый и управляемый результат.

Формула:

```text
Эффективность системы человек-агент =
качество результата
+ скорость
+ управляемость
+ проверяемость
+ понятность
- стоимость контроля
- количество переделок
- когнитивная нагрузка.
```

Что мы делаем:

- измеряем не только скорость генерации кода;
- смотрим, стало ли человеку проще контролировать задачу;
- оцениваем, насколько агент снижает ручную рутину;
- оцениваем, насколько объяснения помогают принимать решения;
- связываем performance с evidence, а не с субъективным ощущением;
- используем insights и coach-инструменты для улучшения процесса.

Инструменты-адаптеры:

- GigaCode /insights;
- VS Code extension AI Engineer Coach;
- run logs;
- evals;
- review metrics;
- lead time metrics;
- developer surveys.
