# Контекст в AI-кодинге

> Рабочая модель по итогам обсуждения. Файл описывает, что такое контекст для кодингового агента, из чего он состоит и почему контекст нельзя путать с истиной проекта.

---

## 1. Короткое определение

Контекст — это рабочая проекция задачи: выбранные данные, решения текущей сессии и следы уже выполненных действий, которые агент использует, чтобы:

- понять задачу;
- выбрать действие;
- изменить систему;
- проверить результат;
- передать работу дальше;
- не потерять связь с проектной реальностью.

Короткая формула:

```text
Контекст = выбранные данные + решения сессии + след действий.
```

Контекст не является одним хранилищем и не равен всей правде о проекте. Это выбранный рабочий набор, дополненный тем, что агент уже решил и сделал в рамках текущей сессии.

В контексте есть три разные части:

- выбранные данные: источники, фрагменты кода, документы, логи, правила, результаты поиска;
- решения сессии: как агент понял задачу, какие допущения принял, какой план выбрал, какие варианты отбросил;
- след действий: команды, изменённые файлы, выводы проверок, ошибки, отклонения, промежуточные артефакты.

У этих частей разная авторитетность, разный срок жизни и разный риск устаревания.

Отдельная практическая проблема — перегрузка контекстного окна. Больше контекста не всегда лучше: если агент загружает всё подряд, релевантные сигналы тонут в шуме, а старые или слабые источники начинают конкурировать с действительно авторитетными.

## 2. Контекст в широком и узком смысле

У слова “контекст” есть два рабочих смысла.

### Контекст в широком смысле

Контекст в широком смысле — это вся информационная среда, из которой агент может брать опору для работы.

Он включает:

- кодовую базу;
- тесты;
- конфиги;
- документацию;
- архитектуру;
- бизнес-требования;
- спецификации;
- контракты;
- правила репозитория;
- системные и developer-инструкции;
- доступные инструменты;
- навыки агента;
- память агента;
- память проекта;
- внешние источники через `MCP`;
- логи;
- результаты проверок;
- историю прошлых действий;
- решения текущей сессии.

В широком смысле почти вся компонентная модель лежит в плоскости контекста: намерение, риск, проверка, актуальность и обучение — это разные типы контекста и разные операции над ним.

### Контекст в узком смысле

Контекст в узком смысле — это то, что реально попало в рабочую область агента в конкретный момент:

- в контекстное окно модели;
- в context pack;
- в результат поиска;
- в краткую выжимку;
- в активный план;
- в handoff summary;
- в текущий scratch-файл.

Узкий контекст всегда является выборкой. Он неполный, ограничен токенами и может быть ошибочно собран.

Короткое различие:

```text
Широкий контекст = всё, откуда агент может брать опору.
Узкий контекст = то, что агент реально использует сейчас.
```

Практический вывод:

```text
Качество AI-кодинга зависит не от объёма контекста,
а от качества отбора, сжатия, навигации и проверки авторитетности.
```

## 3. Контекст не равен истине

Главное правило:

```text
Контекст помогает агенту действовать.
Истина определяется авторитетностью источника, актуальностью и доказательствами.
```

Один и тот же фрагмент контекста может быть:

- авторитетным источником;
- полезной подсказкой;
- устаревшим документом;
- временным выводом агента;
- шумом из поиска;
- evidence о прошлом запуске;
- внешним знанием, которое требует проверки.

Поэтому правильный вопрос не:

```text
Что агент загрузил?
```

А:

```text
Какой это тип контекста?
Для какого решения он применим?
Насколько он авторитетен?
Когда он мог устареть?
Чем он подтверждён?
Стоит ли он места в контекстном окне?
```

## 4. Виды контекста

| Вид контекста | Определение | Примеры | Зачем нужен |
|---|---|---|
| Пользовательский контекст | То, что пользователь явно принёс в задачу | запрос, уточнения, цель, ограничения, критерии успеха | понять намерение и границы задачи |
| Инструкционный контекст | Правила, которым агент обязан следовать | system/developer-инструкции, `AGENTS.md`, правила репозитория, разрешения | понять, как разрешено действовать |
| Кодовый контекст | Фактическая реализация системы | код, тесты, конфиги, схемы, зависимости, миграции | понять текущее поведение и точки изменения |
| Проектный контекст | Долговременные знания о назначении и устройстве системы | бизнес-требования, архитектура, ADR, спецификации, контракты | понять обещанное поведение, ограничения и rationale |
| Операционный контекст | Данные о фактической работе системы | логи, метрики, CI, результаты тестов, runtime traces | понять реальное поведение и симптомы |
| Внешний организационный контекст | Знания вне репозитория | Confluence, Jira, Notion, документация команд, требования из других систем | получить недостающие данные вне кода |
| Агентский контекст | Возможности и состояние самого агента | skills, memory, доступные tools, permissions, текущий режим | понять, что агент умеет и какие у него ограничения |
| Контекст изменения | Описание текущего изменения | намерение, scope, non-goals, acceptance criteria, risk, impact | превратить запрос в управляемую задачу |
| Контекст исполнения | След того, как агент выполняет работу | план, команды, решения, отклонения, изменённые файлы, diff | восстановить ход работы и передать состояние |
| Контекст проверки | Доказательства качества результата | вывод тестов, CI, проверки контрактов, review notes, verification report | доказать, что критерии готовности закрыты |
| Контекст взаимодействия | След общения агента с человеком | вопросы, ответы, статусы, объяснение плана, rationale, handoff summary | держать человека в контуре контроля |
| Контекст эффективности | Данные о том, насколько хорошо работает агент и связка человек-агент | токены, время, переделки, review effort, insights, coach notes | улучшать процесс на основе наблюдений |
| Контекст актуальности | Сведения о возможном рассинхроне знаний | freshness findings, changed paths, устаревшие docs/specs/contracts | понять, что нужно обновить после изменения |
| Исторический контекст проекта | Прошлые решения и события | прошлые PR, инциденты, ретро, lessons learned, старые решения | понять, почему система стала такой |

Эти виды не взаимоисключающие. Один объект может попадать в несколько видов. Например, `ADR` является проектным контекстом, историческим контекстом и потенциальным источником памяти проекта.

## 5. Извлечение и навигация по контексту

Извлечение и навигация — это отдельный процесс. Он отвечает не за “добавить больше данных”, а за то, чтобы агент получил нужный фрагмент нужной авторитетности в нужный момент.

### Извлечение контекста

Извлечение контекста — это поиск, сбор и первичная фильтрация источников.

Что входит:

- поиск по репозиторию;
- чтение конкретных файлов;
- индексный поиск;
- `RAG`;
- `MCP`-запросы;
- получение логов;
- получение результатов тестов;
- чтение спецификаций и контрактов;
- сбор context pack.

Главные вопросы извлечения:

- Что нужно найти?
- Где это может лежать?
- Какой источник сильнее?
- Что могло устареть?
- Достаточно ли найденного для решения?
- Что нельзя класть в окно целиком?

### Навигация по контексту

Навигация по контексту — это движение между уровнями детализации.

Пример:

```text
карта проекта
→ релевантные модули
→ конкретные файлы
→ конкретные функции
→ связанные тесты
→ контракты
→ документы и решения
→ доказательства выполнения
```

Навигация нужна, чтобы агент не пытался держать весь проект в окне.

Что мы делаем:

- начинаем с карты, а не с чтения всего подряд;
- идём от общего к частному;
- держим в окне только активный срез;
- оставляем ссылки на источники;
- возвращаемся к источнику, если summary недостаточно;
- отделяем маршрут поиска от найденной истины.

### Оптимизация контекстного окна

Контекстное окно должно содержать не всё найденное, а только рабочий минимум.

Практики:

- заменить длинный документ на выжимку с ссылкой на источник;
- заменить список файлов на карту модулей;
- заменить полный лог на релевантные строки и временной диапазон;
- вынести длинный trace в артефакт, а в окно положить краткий summary;
- удалить повторяющиеся выводы;
- явно держать список решений сессии;
- явно держать список открытых вопросов.

Хороший context pack:

```text
1. Задача и границы.
2. Релевантные источники.
3. Краткие факты.
4. Принятые решения.
5. Открытые вопросы.
6. Риски и возможный рассинхрон.
7. Ссылки на evidence.
```

## 6. MCP и внешние источники

MCP — это не сам контекст. Это канал получения контекста.

Примеры:

| Канал | Что может дать |
|---|---|
| MCP -> Confluence | бизнес-требования, архитектурные описания, решения команд |
| MCP -> Jira | issue, acceptance criteria, статус задачи |
| MCP -> logs / monitoring | runtime evidence, ошибки, метрики |
| MCP -> test management | результаты тестов, test plans, coverage |
| MCP -> internal docs | политики, runbooks, operational notes |

Правило:

```text
Данные из внешних систем полезны,
но не становятся истиной автоматически.
```

Для них особенно важны:

- дата обновления;
- владелец источника;
- связь с текущей задачей;
- конфликт с кодом, контрактами или спецификациями;
- возможность приложить evidence.

## 7. Контекст прошлых действий агента

Прошлые действия агента — это отдельный вид контекста.

Он включает:

- выполненные шаги;
- команды;
- изменённые файлы;
- diff;
- принятые решения;
- проверенные гипотезы;
- ошибки;
- отклонения от плана;
- результаты проверок;
- handoff summary.

Этот контекст нужен, чтобы агент или следующий исполнитель понимал:

- что уже сделано;
- что проверено;
- где были ошибки;
- какие файлы затронуты;
- какие команды запускались;
- какие вопросы остались открытыми.

Но:

```text
"Я уже проверил" не равно "это правда".
"Я решил, что docs актуальны" не равно "docs актуальны".
"Я изменил файл" не равно "задача выполнена".
```

Прошлые действия агента — это контекст и evidence, но не trusted project knowledge.

## 8. Слоистая модель контекста

Контекст лучше воспринимать слоями, чтобы не перегружать окно агента и не смешивать разные уровни абстракции.

```text
L0. Инструкционный слой
    system/developer instructions, user prompt, AGENTS.md, правила repo.

L1. Целевой слой
    цель задачи, scope, non-goals, acceptance criteria, risk.

L2. Проектный слой
    бизнес-требования, архитектура, ADR, спецификации, контракты.

L3. Кодовый слой
    код, тесты, конфиги, схемы, зависимости, миграции.

L4. Операционный слой
    логи, CI, test reports, runtime traces, мониторинг.

L5. Рабочий слой агента
    планы, impact reports, context packs, run logs, scratch notes.

L6. Исторический слой
    прошлые PR, инциденты, ретро, lessons learned.

L7. Слой доступа
    поиск, индексы, RAG, MCP, generated summaries.
```

Слой доступа не является истиной. Он только помогает найти или собрать другие слои.

## 9. Контекст и память

Контекст шире, чем память.

```text
Память проекта — это curated knowledge.
Контекст — это всё, что агент использует в конкретной задаче.
```

Например:

| Объект | Это контекст? | Это память проекта? |
|---|---|---|
| `AGENTS.md` | да | частично, как правило работы |
| prompt пользователя | да | нет |
| код | да | источник фактической реализации |
| ADR | да | да, как rationale |
| Confluence page | да | нет, пока не промотирована или не подтверждена |
| context pack | да | нет, derived artifact |
| run log | да | нет, это evidence/history |
| agent scratch note | да | нет |
| stable spec | да | да |

Ключевое правило:

```text
Полезный контекст может стать памятью проекта
только после проверки, review и promotion.
```

### Виды памяти

Память в AI-кодинге тоже не одна.

| Вид памяти | Определение | Примеры | Риск |
|---|---|---|---|
| Память агента | То, что относится к самому агенту и его устойчивым предпочтениям/навыкам | skills, long-term memory, предпочтения пользователя, прошлые паттерны работы | агент может применить старый паттерн не к той задаче |
| Память проекта | Долговременное авторитетное знание проекта | stable specs, ADR, контракты, правила, code maps, reviewed facts | может протухнуть или конфликтовать с кодом |
| Сессионная память | То, что возникло в текущей рабочей сессии | принятые решения, план, допущения, найденные факты, trace действий, вопросы человеку, объяснения, статусы, наблюдения об эффективности | не является истиной, пока не подтверждена и не промотирована |

Короткая формула:

```text
Память агента = что агент умеет и помнит о стиле работы.
Память проекта = что проект устойчиво знает и обещает.
Сессионная память = что было решено и сделано сейчас.
```

Правило:

```text
Сессионная память может стать памятью проекта
только через проверку, владельца и ревью.
```

## 10. Намерение и спецификация

Намерение и спецификация — это не одно и то же.

### Намерение

Намерение — это смысл запроса: зачем пользователь хочет изменение и какую проблему он пытается решить.

Намерение отвечает на вопросы:

- зачем это нужно?
- какую боль или цель закрываем?
- кто ожидает результат?
- что будет считаться полезным исходом?
- какие ограничения важны для пользователя?

Примеры намерения:

```text
Снизить количество ошибок авторизации после истечения access token.
Упростить onboarding нового разработчика.
Сделать поведение API совместимым с новым клиентом.
```

### Спецификация

Спецификация — это явное описание ожидаемого поведения системы после изменения.

Спецификация отвечает на вопросы:

- что именно должно измениться?
- какие сценарии должны работать?
- какие сценарии не входят в задачу?
- какие исключения возможны?
- какие контракты или документы затронуты?

Пример спецификации:

```text
Если access token истёк, API возвращает 401.
Если refresh token валиден, клиент может получить новый access token.
Если у пользователя нет нужной роли, API возвращает 403.
Logout инвалидирует refresh token.
Модель ролей в этой задаче не меняется.
```

### Критерии готовности

Критерии готовности — это проверяемые условия, по которым можно сказать, что спецификация выполнена.

Они отвечают на вопросы:

- чем докажем, что поведение реализовано?
- какие тесты или проверки нужны?
- какие edge cases обязательны?
- что должно быть приложено как evidence?

Коротко:

```text
Намерение = зачем.
Спецификация = что должно быть.
Критерии готовности = как проверим.
```

## 11. Контекст и авторитетность

У разных источников контекста разный вес.

Примерные вопросы:

| Вопрос | Более сильные источники |
|---|---|
| Что сейчас реализовано? | код, тесты, runtime evidence |
| Что система обещает наружу? | контракты, API specs, схемы |
| Что должно быть по требованиям? | stable specs, бизнес-требования, acceptance criteria |
| Почему было принято решение? | ADR, design docs, review notes |
| Что агент уже сделал? | run logs, commands, diff, handoff |
| Что может быть устаревшим? | freshness findings, changed paths, ownership rules |

Конфликт источников — это не повод автоматически переписать один источник под другой.

Это drift event:

```text
код не совпадает со spec;
contract не совпадает с реализацией;
Confluence говорит одно, tests другое;
agent summary не подтверждается diff;
run log говорит "проверено", но evidence отсутствует.
```

## 12. Как агент должен работать с контекстом

Перед использованием контекста агент должен ответить:

1. Какую задачу я решаю?
2. Какой тип контекста нужен для этого решения?
3. Какие источники авторитетны?
4. Какие источники являются временными или сгенерированными?
5. Что могло устареть?
6. Где есть конфликт?
7. Какие доказательства нужны?
8. Что нужно сохранить для handoff?

Минимальный protocol:

```text
1. Прочитать prompt пользователя и правила repo.
2. Найти active change или сформулировать его.
3. Выбрать релевантный project/code/operational context.
4. Отделить authority sources от search results и generated summaries.
5. Записать рабочие выводы агента отдельно от stable knowledge.
6. После изменения сохранить evidence и историю действий.
7. Проверить, какие знания могли устареть.
```

## 13. Формула для слайдов

Короткая версия:

```text
Контекст = выбранные данные + решения сессии + след действий.
```

Расширенная версия:

