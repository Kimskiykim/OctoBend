# Review PDF: AI DISRUPT PDLC v3

> Источник: `AI_DISRUPT_PDLC_v3.pdf`.
> Цель review: понять, какие термины и идеи из PDF полезно взять в нашу framework-independent модель AI-кодинга, а какие лучше оставить как внешние/enterprise-specific.

---

## 1. Краткий вывод

PDF хорошо подтверждает наше направление: AI-кодинг нужно обсуждать не как “выбор агента”, а как трансформацию процесса, ролей, контекста, спецификаций, проверки, платформы и метрик.

Самые полезные идеи для нашей модели:

- разделение на человеческую петлю намерения и агентную петлю реализации;
- specification-driven development как управляющий слой между человеком и агентом;
- context engineering как отдельная инженерная дисциплина;
- контекст как стратегический актив, но также как источник риска;
- token budget / token economics как операционная метрика;
- eval-driven development как способ улучшать агентов и workflow;
- session handoff как обязательный механизм долгих задач;
- IDP / Golden Path / Paved Roads как enterprise-реализация control model;
- governance должен быть встроен в инструменты, а не существовать только как политика;
- эффективность нужно мерить не только скоростью, но и качеством, вмешательством человека, стоимостью и соответствием спецификации.

Главная поправка к нашей модели:

```text
Наша модель остаётся framework-independent control model.
PDF даёт хороший словарь для enterprise-реализации этой модели:
IDP, Golden Path, SDD, Context Engineering, Evals, Token Economics, Governance.
```

## 3. Термины, которые стоит взять

### Сильные термины для презентации

| Термин | Русское объяснение | Где использовать |
|---|---|---|
| `Intent Loop` | человеческая петля формирования намерения, альтернатив, решений и спецификации | верхнеуровневая диаграмма |
| `Implementation Loop` | агентная петля реализации, тестов, CI и подготовки результата | верхнеуровневая диаграмма |
| `Specification-Driven Development` / `SDD` | разработка, где спецификация является управляющим артефактом для человека и агента | слайд про intent/spec/acceptance |
| `Context Engineering` | дисциплина отбора, структурирования, сжатия и подачи контекста агенту | слайд про контекст |
| `Context-Driven Engineering` | организация разработки вокруг machine-readable контекста | для IT-лидеров и стратегии |
| `Context rot` | деградация качества контекстного окна из-за шума, устаревания и размывания внимания | слайд про проблемы контекста |
| `Context poisoning` | попадание ошибки или галлюцинации в persistent context с последующим размножением | слайд про риски памяти |
| `Just-in-time context` | подгрузка нужного контекста в момент необходимости, а не всё заранее | практики оптимизации токенов |
| `Token budget` | лимит токенов как управляемый ресурс задачи | performance / cost |
| `Token Economics` / `TokenOps` | управление стоимостью AI-исполнения | platform / enterprise metrics |
| `Eval-driven development` | улучшение агента и workflow через систематические evals | verification + learning |
| `Specification Compliance Rate` | доля требований спецификации, корректно реализованных с первого раза | performance агента |
| `Human Intervention Rate` | доля задач, где потребовалось ручное вмешательство | эффективность системы человек-агент |
| `Session Handoff Protocol` | стандарт передачи состояния между агентными сессиями | execution / orchestration |
| `Quality Gate` | обязательная проверка перед продвижением изменения | verification / governance |
| `Golden Path` | рекомендуемый end-to-end маршрут задачи через платформу | policies / recipes / tooling |
| `Paved Roads` | стандартные маршруты и шаблоны, удобные по умолчанию | adoption / IDP |
| `Context Sanitizer` | слой очистки контекста от секретов, PII и unsafe data | security / governance |
| `Audit Logger` | неизменяемая фиксация AI-запросов, контекста и действий | evidence / audit |

### Термины, которые использовать осторожно

| Термин | Почему осторожно |
|---|---|
| `AI-native` | звучит стратегически, но может быть слишком широким и маркетинговым |
| `Zero-Friction SDLC` | сильная метафора, но обещает слишком много; контроль всё равно нужен |
| `код как эфемерный артефакт` | для IT-лидеров может быть провокационно; лучше говорить “спецификация становится более важным управляющим артефактом” |
| `продакты создают ПО без инженеров` | может отвлечь от нашей темы; лучше говорить о смене границ ролей |
| `полная автономия агентных команд` | пока лучше оставить как roadmap/экспериментальную зону |

## 4. Как PDF меняет нашу смысловую карту

Наша текущая карта:

```text
контекст → намерение → спецификация → исполнение → проверка → evidence
         ↘ память / freshness / learning / объяснение / performance
```

После PDF стоит добавить явный верхний слой:

```text
Intent Loop:
человек формирует намерение, альтернативы, решения, спецификацию

Implementation Loop:
агент реализует, проверяет, собирает evidence, передаёт результат

Control Platform / Governance:
правила, маршруты, gates, логи, контекст, метрики
```

Но важно не заменить нашу карту двухпетлевой моделью. Лучше использовать её как более простое объяснение:

```text
Две петли объясняют, где работает человек и где работает агент.
Наша компонентная модель объясняет, чем нужно управлять внутри и между петлями.
```

## 6. Что добавить в презентационный тезис

Текущий тезис:

```text
Фреймворки можно менять.
Фундаментальные задачи AI-кодинга остаются.
```

Усиленная версия после PDF:

```text
AI-кодинг — это не ускоренный SDLC и не набор IDE-плагинов.
Это новая control system вокруг изменения:
человек формирует намерение и спецификацию,
агент исполняет и проверяет,
а платформа удерживает контекст, governance, evidence и метрики.
```

Для IT-лидеров:

```text
Побеждает не команда с самым модным агентом,
а команда, которая умеет управлять контекстом,
спецификацией, проверкой, стоимостью и взаимодействием человек-агент.
```

## 7. Что не брать напрямую

PDF местами строит сильную enterprise-платформенную рамку вокруг IDP. Для нашей текущей презентации это полезно как реализация, но не должно становиться центром.

Не стоит делать главным:

- IDP как обязательную тему всех слайдов;
- AI-native platform architecture;
- подробную дорожную карту внедрения;
- регуляторный compliance;
- FDE-модель;
- 8 уровней зрелости как основной фреймворк.

Почему:

```text
Наша цель — объяснить универсальные компоненты AI-кодинга.
IDP, Golden Path и Governance — способы enterprise-реализации этих компонентов.
```

## 9. Итог

PDF не отменяет нашу модель, а хорошо её усиливает.

Что у нас было сильнее:

- чёткое различие “контекст не равен истине”;
- разложение памяти на агентскую, проектную и сессионную;
- эффективность человека с агентом как отдельная метрика;
- объяснение как функция агента;
- framework-independent позиционирование.

Что PDF добавляет:

- профессиональные термины для контекста и спецификаций;
- двухпетлевую рамку человек/агент;
- язык enterprise-платформы;
- конкретные метрики AI-DLC;
- риски context rot / context poisoning;
- eval-driven improvement loop.

Финальная рекомендация:

```text
Использовать PDF как терминологический источник и validation нашей модели,
но не подменять нашу модель концепцией AI DISRUPT PDLC.
```
